# Building and running the handshake Core

`core/` holds the elaborated Core of the two-peer handshake program as Lean
source, with one module per WireGuard C file (see `core/README.md`), and the
runner `linked-run`, which executes the program's `main` (the test function in
`scenario/handshake.c`) with the Cerberus-Lean evaluator and prints its
verdict. Running it checks that the verdict is the expected one:

    Defined {value: "Specified(0)", stdout: "<expected/handshake.stdout>", stderr: "", blocked: "false"}

That is, `main` returns 0, has defined behaviour throughout, and prints exactly
`expected/handshake.stdout`.

Requirements: x86-64 Linux (tested on Debian 12), 16 GB of RAM, about 10 GB
of free disk. All commands below are run from a shell; `$RELEASE` is the
directory of this repository.

## 1. Install the toolchain

The Core is executed by the Lean port of Cerberus from branch
`wireguard-handshake` of
<https://github.com/mathematics-inc/cerberus-lean-upstream-publish>: commit
`b735d7bdcff9570ed7dce3278d829086b1c008d8` contains the additions this program
needs, squashed onto upstream revision `c4284b0`. Lean 4.32.2 builds it; Lem
(Lean backend) generates part of its source from the Cerberus model, which
needs OCaml.

Packages (Debian 12):

    sudo apt-get install build-essential git curl ca-certificates opam \
        libgmp-dev pkg-config m4 unzip patch python3 python3-venv
    curl https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh -sSf | sh

OCaml 5.4.0, Dune and Lem:

    opam init --bare --no-setup --disable-sandboxing
    opam switch create cerberus-lean ocaml-base-compiler.5.4.0
    eval "$(opam env --switch=cerberus-lean)"
    opam install dune.3.23.1
    opam pin add lem git+https://github.com/OathTech/lem-lean.git#2d3a492758cb23dc4e417f2961983d25b36ce130

Lean:

    elan toolchain install leanprover/lean4:v4.32.2

## 2. Build and run the Core

`core/lakefile.toml` requires the evaluator by commit
(`b735d7bdcff9570ed7dce3278d829086b1c008d8` of branch
`wireguard-handshake`, directory `lean_frontend`). Part of its Lean
source is generated by its own build, so fetch it, generate those sources,
then build:

    cd "$RELEASE/core"
    lake update
    (cd .lake/packages/CerberusLean && make lean-prelude-src && make lean-native-obj)
    LEAN_NUM_THREADS=2 lake build
    LEAN_ABORT_ON_PANIC=1 .lake/build/bin/linked-run >../verdict.txt 2>../stderr.txt
    cd .. && sh test/compare.sh verdict.txt stderr.txt

`make lean-prelude-src` runs Lem to generate the evaluator's Lean model
sources; `make lean-native-obj` compiles its native helper. Both need the
OCaml switch above on `PATH`.

`lake build` builds the evaluator, then elaborates the 20 modules of `core/`,
compiles them to C and links the runner. Elaborating one module takes up to
about 4.9 GB (4.6 GiB) of memory; the largest are `WireGuard/Noise.lean` and
`Support/Part09.lean`. Lake elaborates as many modules at once as there are
cores; `LEAN_NUM_THREADS=2` keeps the build within 16 GB. On an 8-core machine
the build from a fresh clone took about 40 min. It writes about 4.8 GB
(4.5 GiB) under `core/.lake`: about 1.5 GB of `.olean`/`.ilean`, 2.0 GB of
compiler intermediates (0.9 GB of it generated C), a 570 MB runner, and
0.68 GB for the evaluator package.

`linked-run` takes about 2 h 15 min. It accepts
`--fuel N` (default 2·10¹², enough for this program); exhausting the fuel is
reported and is not a pass. `LEAN_ABORT_ON_PANIC=1` turns an internal panic
of the evaluator into an abort rather than a value. `linked-run --check`
checks that the definitions reassemble to the elaborated Core, by digest;
`linked-run --roundtrip . ..` renders the program again and checks that it
reproduces the 20 modules byte for byte.

`test/compare.sh VERDICT [STDERR]` prints `PASS ...` and exits 0 when the
verdict equals the expected line above and the standard error is empty;
otherwise it shows the verdict and exits 1. It also reads a verdict on
standard input (`... | sh test/compare.sh -`).

## 3. Check the expected output independently

    python3 oracle/check.py

`oracle/` recomputes the protocol observations in `expected/handshake.stdout`
from the WireGuard protocol specification, using Python's BLAKE2s and
pyca/cryptography for X25519 and ChaCha20-Poly1305, and none of this
repository's C code. It installs the pinned wheels into a virtual environment
(network access is needed the first time) and fails unless every observation
agrees.

## Recorded run

`results/` records the run of this Core: the command, the evaluator revision,
the verdict, time and memory.
